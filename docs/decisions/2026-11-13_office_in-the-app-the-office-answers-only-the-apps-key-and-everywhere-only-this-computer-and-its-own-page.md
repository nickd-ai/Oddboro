- [office] **Decision (2026-11-13): in the desktop app the office answers only requests that carry the app's key, and every office answers only this computer, only at its own names (127.0.0.1, [::1], localhost, its addresses through Caddy and the app's ORIGIN), and takes an action (anything but GET, HEAD or OPTIONS) only from the owner's own page, the app's shell, or an Odd's run at its gateway.** Any program on the owner's computer can send the office a request with whatever headers it likes. So in the app (ODDBORO_APP) the shell makes a fresh random key every time it starts Node, keeps it only in memory, and hands it to Node as the first line on Node's stdin; a key that leaks once its Node is gone opens nothing. Before the shell trusts the server on the port, at every start, the server proves it holds that key by answering a fresh nonce with HMAC-SHA256 under the key of a fixed label and the nonce (`/api/proof`, the one other route open without the key), so a program that took the port never gets the window's cookie. It is never in a file, the Keychain, the environment or a command line, since any program running as the owner can read another's environment (`ps -E`). The window carries it in an HttpOnly, SameSite=Strict session cookie the shell sets before the window asks for anything, and the window's pages may load only from the office itself, data, blob and https, since a cookie names no port. The shell's own requests (`/api/update`, `/api/browser-link`) carry it in a header, which retires the update token. Without the key only the sign-in callbacks (GETs, each checking its own state), a run's gateway call with its token, and a link the office makes for the owner's browser (once, for one path, within a minute) get in; everything else gets 403, reads too. An office run from source has no key and keeps the other rules. A request comes from this computer when the connection's address and every address in X-Forwarded-For are loopback: through Caddy, which listens on every address on a Mac and Linux, the address Caddy forwards for is what keeps another machine out. The page is told apart by what the browser says (Sec-Fetch-Site, or with none an Origin naming the host asked), since through Caddy the page is https and the office http, and the names refuse a site that points its own name at this computer. The built server serves the page's built files before the check. Under `vite dev` the this-computer rule also runs before Vite's own routes and its websocket, and Vite's `/__open-in-editor` is refused outright. Supersedes the 2026-11-11 ruling. Code in `apps/office/src/lib/server/app-key.ts`, `owner-page.ts` (`guardOffice`), `this-computer.ts`, `apps/office/vite.config.ts` and `apps/desktop/src-tauri/src/key.rs`; the detail is in `apps/office/CLAUDE.md`, "Who the office answers".
