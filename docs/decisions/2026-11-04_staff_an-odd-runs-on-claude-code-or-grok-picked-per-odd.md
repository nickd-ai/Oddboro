- [staff] **Decision (2026-11-04): an Odd runs on Claude Code or on Grok, picked per Odd under "Runs on" in the hire drawer and on its Settings tab, and never falls back to the other.** Grok is a second coding tool for owners who have it: `staff.agent` keeps the pick, a switch clears the Odd's chat session and is refused while it replies, and a computer without the picked tool fails the run naming it. Each tool takes one model office-wide from `.env` (`OFFICE_MODEL`, `OFFICE_GROK_MODEL`). Grok runs as `grok -p` from the office's own Grok home, `<ODDBORO_HOME>/grok`, never the owner's `~/.grok`. The owner signs in to that home from the office's page (the 2026-11-04 sign-in decision), and a run from a home with no sign-in fails pointing there, since Grok's own advice (`grok login`) signs in `~/.grok`; every compatibility cell Grok has an environment variable for is switched off on each run, and the office writes a `config.toml` only into a home with none, since that file belongs to the sign-in. A Grok Odd reads the owner's data folder as a Claude Code Odd does, since which tool an Odd runs on is the owner's choice per Odd. Its files are held by a kernel sandbox profile per Odd (per run on a thread) built on Grok's `strict`, which reads the Odd's folder, the owner's data folder, its thread's folder (or, in a lead's chat, the folder of each live goal it leads, as a Claude Code lead's chat does), node and the tool server's code, and writes the Odd's folder, its part of the thread, Grok's own temp folder and Grok's sessions folder, with `~/Library`, `/Library`, `/tmp` and `/var` shut. Measured on Grok 1.0.46 on a Mac against a made-up home, the kernel refused `~/Documents`, `~/Desktop`, `~/.ssh`, `~/.aws`, `~/.config`, `~/Library`, the home folder, another Odd's folder, the rest of the office's home, the repo's `data/`, `/private/tmp` and the temp folder. The kernel still lets a run read Grok's home (the sign-in and every Grok Odd's sessions), node's folder, the code's `packages` and `node_modules`, and `/usr`, `/bin`, `/sbin`, `/etc`, `/dev`, `/System` and `/private/etc`; those are held only by Read deny rules, and `/etc` stays readable because Grok will not start without it. Every deny rule names the folder itself and everything in it, since a rule on `<folder>/**` alone let list_dir and grep read the whole folder (measured). With both, list_dir and grep at Grok's home, node's folder and the code's `packages` and `node_modules` were refused (measured), so a Grok home per Odd is not needed. The sessions folder the kernel lets a run write holds every Grok Odd's sessions, so Edit and Write deny rules on Grok's home hold it as well as `dontAsk` (measured: a write there was refused). A Grok call with no allow rule is refused under `dontAsk`, and a run that ends on one is accepted, since it fails closed. A Grok run gets no `NODE_OPTIONS`, because a preload outside the sandbox stops the tool server from starting. The New Altitude team allows 21 Grok requests a minute (measured), and the office does not pace Grok runs against it. The profile holds the whole grok process (measured), so Grok could not save a renewed sign-in, and once it ran out runs waited on 401s, silent in the stream, until the 20-minute cut. Grok takes only folders in `read_write` and has no renew command, so before a run the office reads only `expires_at`; with less than the run's limit plus 10 minutes left it runs `grok models` outside the sandbox, which renews it on disk (measured), and refuses a run whose sign-in is still past, pointing to the sign-in. Code in `apps/office/src/lib/server/grok.ts`; `apps/office/CLAUDE.md` item 9 lists the rules. The 2026-11-06 ruling supersedes its file tools: the office's carry its files, this profile a second wall.
